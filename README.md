# ABB Round 2 - Tic Tac Toe

A browser-based Tic Tac Toe application implemented with:

- Angular 19 + TypeScript
- .NET 8 ASP.NET Core Web API
- REST APIs
- In-memory backend state
- xUnit unit tests

## Design decisions

1. The backend is the source of truth for board state, turns, move history, game status and scoreboard.
2. The backend validates every move; the frontend never decides whether a move is legal.
3. Two modes are supported:
   - Two Player: X and O are human players.
   - Computer: X is human and O is computer.
4. Computer moves are generated by the backend immediately after a valid X move.
5. Undo behavior:
   - Two Player: removes one move.
   - Computer: removes the human X move and the following computer O move together.
6. Option A from the problem statement is selected: Undo is disabled after a game is completed. This keeps the scoreboard final and avoids retroactively changing completed results.
7. Scoreboard is process/session scoped and stored in memory. Restarting the API clears it.

## Prerequisites

- .NET 8 SDK
- Node.js 20.11+ recommended
- npm
- Angular CLI 19

Install Angular CLI:

```bash
npm install -g @angular/cli@19
```

## Run backend

```bash
cd backend/TicTacToe.Api
dotnet restore
dotnet run
```

The API listens on:

- http://localhost:5000
- https://localhost:5001

Swagger:

- http://localhost:5000/swagger

## Run frontend

In another terminal:

```bash
cd frontend
npm install
ng serve
```

Open:

http://localhost:4200

The Angular development server proxies `/api` calls to `http://localhost:5000`.

## Run tests

```bash
cd backend/TicTacToe.Tests
dotnet test
```

The tests cover valid/invalid moves, turn switching, row/column/diagonal wins, draw, reset, undo in both modes, scoreboard updates, computer move selection and moves after completion.

## REST API

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/games` | Create a game |
| GET | `/api/games/{id}` | Get game state |
| POST | `/api/games/{id}/moves` | Submit a move |
| POST | `/api/games/{id}/undo` | Undo according to game mode |
| POST | `/api/games/{id}/reset` | Reset current game |
| GET | `/api/scoreboard` | Get scoreboard |
| POST | `/api/scoreboard/reset` | Reset scoreboard |

Create game request:

```json
{
  "mode": "TwoPlayer"
}
```

or

```json
{
  "mode": "Computer"
}
```

Move request:

```json
{
  "player": "X",
  "cell": 4
}
```

Cells are zero-based from 0 to 8:

```text
0 | 1 | 2
---------
3 | 4 | 5
---------
6 | 7 | 8
```

## Computer strategy

The computer follows the exact priority from the exercise:

1. Win if O has a winning move.
2. Block X if X has a winning move.
3. Take center.
4. Take a corner.
5. Take any remaining cell.

## Suggested review flow

1. Start in Two Player mode.
2. Demonstrate a row win.
3. Reset game and demonstrate undo.
4. Demonstrate draw.
5. Reset scoreboard.
6. Switch to Computer mode.
7. Show that the backend automatically adds O's response.
8. Demonstrate computer undo: both X and O moves are removed.
9. Try an occupied cell and verify the backend rejects it.
10. Run `dotnet test`.

## AI-assisted development notes

AI can be used for scaffolding, test-case generation and review, but the candidate should be able to explain:

- Why backend validation is authoritative.
- Why the game state is protected by a per-game lock.
- Why scoreboard updates happen only during a transition from InProgress to Won/Draw.
- Why undo is disabled after completion.
- How the computer priority algorithm works.
- Why in-memory state is acceptable for this exercise and what would change for production.

## Known limitations

- State is in memory, so restarting the API loses games and scoreboard.
- The implementation is intended for a local interview exercise, not multi-instance production deployment.
- No authentication is required by the problem statement.
- For production, state would move to a durable store and distributed locking/session coordination would be required.
